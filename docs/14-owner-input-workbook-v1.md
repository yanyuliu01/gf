# Owner 输入工作簿 v1

状态：**待 Owner 填写** ｜ 日期：2026-08-07
对应任务：`OWN-001` 至 `OWN-006`、`OWN-008` ｜ 任务状态以 `../TODO.md` 为准

这份工作簿只收集必须由你判断的产品、世界与角色语义。它不是 Prompt、
Schema 或 Utility 参数文件，也不要求你写代码。工程侧会把签字后的内容
转成版本化契约、测试样例和 Prompt 派生产物。

填写原则：

- 优先写具体例子，不追求一次定义所有规则；
- 描述世界如何运作，不预写剧情节拍；
- 描述角色同时成立的欲望与冲突，不写“遇到 X 就做 Y”；
- Utility 只标事件对关切的影响，不给动作打分；
- 认知精力只描述体感与能力后果，不填写 token、余额、百分比或价格；
- 不确定可以写“先按建议默认值试跑”，以后通过事件和版本修改。

## A. 世界运行规则（OWN-001）

现有 `docs/06` 与 S2 已经有充足的世界观、跨世界边界、人物与地点事实。
这里补的是“模拟器如何让这些事实动起来”，不是重写泰拉设定。

当前主草案是
[`16-computable-world-model-draft-v1.md`](16-computable-world-model-draft-v1.md)：
它把世界定义为资源禀赋、库存-流量、生产过程、容量、生态/身体规律和离散事件组成
的可编码状态转移系统。此前的
[`15-world-runtime-interaction-rules-draft-v1.md`](15-world-runtime-interaction-rules-draft-v1.md)
只保留为开放行动的交互/裁定接口，不能单独完成 `OWN-001`。请先审 16 的 §16，
再把确认结果记录到本工作簿；任何草案存在本身都不表示 `OWN-001` 已完成。

### A0. 可计算世界内核（先完成）

docs/16 已给出公式与工程默认值。Owner 先确认语义，不需要直接填写数值系数：

| 主题 | 建议默认值 | Owner 决定 |
|---|---|---|
| 模型内核 | 混合离散事件 + 库存-流量 + 生产过程网络 |  |
| MVP 边界 | 缪尔赛思个人、生态园、生态科和特里蒙外部边界 |  |
| 资源法则 | 库存、货币、容量、状态、信息、权限六类数学语义 |  |
| 非资源项 | 关系、情绪、关切和科研灵感不做可交易库存 |  |
| 流形 | 连续控制负荷与有界差错，不设固定数量上限 |  |
| 时间尺度 | 人与工序用分钟/小时，植物与慢变量用小时/日 |  |

再给出以下种子内容，写“充足/正常/偏紧/短缺”和大致耗时即可：

1. 生态科最重要的 8-12 个资源账户；
2. 最常发生的 3-5 条生产链；
3. 最紧缺的人员、设备、空间或审批容量；
4. S-4 及另外 2-3 个植物群组的当前状态和适宜环境；
5. 普通采购交期、预算周期、排班和维护关系；
6. 可以由运行时生成的天气/供应扰动，以及必须由 Owner/canon 提供的外部事件。

以下 A1-A5 仍用于行动裁定和 NPC 交互，但要建立在 A0 的计算世界上，不能反过来
用自然语言事件代替资源和生产状态。

## B. Concern 与人格张力（OWN-002）

Concern 是“什么对她有意义”，不是目标枚举、情绪标签或行为规则。
它可以开放增长，但每条都需要来源、身份和生命周期。

### B1. Concern 卡模板

```text

可能支持它的事件例子（不是行为规则）：
可能伤害它的事件例子：
影响通常短暂、跨天还是长期：
哪些相似 concern 应与它合并：
哪些解释是对她的误读：
Owner：接受 / 修改 / 拒绝
```

### B2. 建议种子（请逐条接受、修改或拒绝）

| ID | 建议自然语言关切 | 主要张力 | Owner 决定 |
|---|---|---|---|
| `concern_find_kin` | 想知道大地上是否还有同类，也害怕所有答案最终仍指向“只剩她一个” | 追寻答案 vs 回避最终确认 |  |
| `concern_shelter_fragile_life` | 想给脆弱生命一个能自由栖居的地方，包括她自己 | 保护生命 vs 组织、资源与科学现实的代价 |  |

### E2. 建议覆盖的八类剧本

1. “你最近有点烦”的含糊边界反馈与后续重新理解。

## G. 认知精力体感校准（OWN-008）

你已经确认以下语义方向，工程侧不得在实现时反向改写：

- 角色实际理解的上下文、内部思考和最终表达都会消耗认知精力；
- 她能感到疲劳、注意变窄、难以继续深入，但不知道 token、余额、百分比、API
  价格或运营限额；
- 供应商计费、缓存折扣、协议字段、Schema 修复、基础设施重试不构成她的生活体验；
- 同一段她实际读过的语义，即使服务端命中缓存，仍然形成认知负荷；
- 休息与睡眠可以恢复精力，恢复还会受到身体状态和当前活动影响；
- 精力约束她此刻能投入多少认知劳动，但不能替她选择语义行动，也不能变成有限
  行为候选或行为树；
- Affect 关闭时这套机制仍完整存在；Affect 不能直接改写精力账户；
- 系统成本上限不能伪装成她疲惫、内疚或不愿回应。

参数换算由工程侧用冻结任务集标定。你只需要补下面的相对体感和边界，不需要接触
任何机器数值。

### G1. 疲劳层次

```text
轻微疲劳时，她主观上更像什么：
明显疲劳时，哪些能力会先下降（注意、推演深度、表达长度、切换任务等）：
深度疲劳时，她仍然必须保留哪些基本能力：
哪一种“累”的写法最不像她、绝不能进入对话：
```

### G2. 恢复轮廓

```text
短暂停顿、安静活动、睡眠三者的恢复差别：
身体不适或持续工作怎样影响恢复体感：
什么情况下休息后应明显恢复：
什么情况下睡过一觉仍应有残余疲劳：
```

### G3. 最小诚实回应

当博士发来消息但她已经很累时，请各写一个你认可的例子。重点是“完整、诚实、像她”，
不是固定台词或触发规则。

```text
仍能正常聊，但不想展开：
只能先给一个短而完整的回应：
需要明确推迟深入讨论，并留下可履行承诺：
即使很累也不能出现的敷衍、截断或情绪勒索：
```

### G4. 质性签字

- [ ] 接受上述已确认语义，先按工程默认标定试跑。
- [ ] 接受方向，但需要修改以下体感或恢复边界：____________________。
- [ ] 暂不决定具体层次；只冻结“消耗、不可见数值、可恢复、非行为选择器”四条。

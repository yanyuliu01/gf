## 1. 为什么要重裁

v1 提交于 2026-08-05 23:20。它有两处上下文缺陷，导致裁决结果不可靠：

**缺陷一 · 只看到补充方案的摘要，没有全文。**
后果是 v1 采用了「27 行采纳矩阵」这种按标题裁决的形式。标题级裁决能挡住危险主张，但看不见正文里的可实现结构。补充方案中六处最接近工程规范的内容——§4.2 唤醒条件、§4.3 离线追赶流程、§4.4 事件来源分类、§4.7 涌现前提、§5.3 候选动作结构、§13.1 因果链观测规格——在 v1 里要么被压成一行「直接采纳→M2」，要么根本没出现。

**缺陷二 · 没有完整的项目文档与 canon。**
后果是 v1 无法判断某条补充「其实已经有了」还是「确实是新的」，只能保守地判「采纳/延后」。最严重的例子是：v1 把世界母版、组织资源、具名 NPC 统统判给 M5，却不知道 `docs/06` 的 A3/A4/A6 **已经写好了** 4 个地点、5 条线索、5 件物件、2 名 NPC、8 条创世日志和完整的联想采样配置。真正的问题不是「还没设计」，而是「设计完了没有容器装、没有代码加载」。这两者的修复成本相差一个数量级。

补充说明：v1 还早于 M1 运行时代码（`7cfe56c`，08-06 00:00）。它在零实现的前提下判断「什么该延后」，容易把「现在做不了」误判成「M5 再做」。

**本次重裁的输入**：补充方案全文 1052 行、`docs/01`–`docs/11` 全文、12 份 JSON Schema、`migrations/001_initial.sql`、`prompts/` 全部现役资产、`corpus/canon` 三表统计，以及 `src/gf/` 的 4178 行运行时代码与 19 个通过的测试。

## 2. 裁决判据

沿用项目既有的三条审计判据（`docs/README` §设计原则的演进史），并补充第四条：

1. 这个结构描述的是**客观事实**（来源、去向、真假、可见性、能力）还是**主观/涌现现象**（心情、亲疏、进度、投入度）？后者一律拆。
2. 它是在**描述她**，还是在**替她做决定**？后者一律拆。
3. 一条常驻的人物描写，如果能被写成「遇到 X 她会 Y」，它就写错了。
4. **（本次新增）** 这条补充是「项目缺少的机制」，还是「项目已有但缺容器/缺加载」？后者不该进采纳矩阵，该进缺陷清单——把实现债记成设计债会让路线图失真。

裁决词统一为四种：

| 裁决 | 含义 |
|---|---|
| **已覆盖** | 项目现役权威已有等价或更严格的规定，无需动作 |
| **需并入** | 补充提供了项目缺少的可实现结构，须由指定权威文档正式吸收 |
| **需改写** | 方向正确但形态违反判据，给出改写后的形态 |
| **拒绝** | 与项目已确立原则冲突，记录理由以防再次提出 |
| **不适用** | 面向多用户通用产品，本项目单用户单实例场景下不成立 |

### 3.2 §4 World Engine —— 本次重裁的重点

v1 只裁决了 §4 的「事实权归属」一点，§4.1–§4.7 的其余内容全部未处理。这是 v1 最大的遗漏，也正是项目世界层空缺的原因。

#### §4.1 两层世界模型 —— **需并入（最高优先级）**

补充提出 Canonical World（母版，不可由单次运行改写）与 User World Instance（实例，运行时动态状态）分层。

**改写后并入形态**（本项目单用户，「每用户实例」维度取消，但分层保留）：

| 层 | 内容 | 权威 | 可写性 |
|---|---|---|---|
| **母版层** | `corpus/canon` 三表 + `docs/06` A1–A6 种子 + `prompts/slots/S1/S2` | Owner 策展 | 运行时**只读**；变更须经 Owner 与版本化种子 |
| **实例层** | `world_state`、`persona`、`inventory`、threads、debts、**entities**、**locations** | 事件账本 + reducer | 运行时可写，单写者提交 |

**为什么这是最高优先级**：项目当前缺的正是实例层里 entities 与 locations 两类容器。`docs/06` A3 已经写好 4 个地点和 2 名 NPC，A6 的联想采样池第一项就是 `entities`——但 `migrations/001_initial.sql` 里没有 entities 表也没有 locations 表，`reducers.ts` 的 `PatchOp.target` 只支持 `world_state | thread | persona | inventory | debt`。**采样池的第一类燃料在运行时无处安放。**

并入去向：`docs/02 §2.1`（补两层模型声明）、`migrations/002`（新增 entities/locations）、`schemas/patch-op.schema.json`（扩 target 枚举）。

#### §4.2 事件驱动时间与唤醒条件 —— **需并入**

补充给出 7 个唤醒时机：计划行动开始/结束、资源或地点或人物条件满足、用户消息到达、关系事件或社会请求到达、内生动机越过有意义阈值、承诺到期或冲突升级或反思窗口、系统事件按世界规则发生。

项目现状：`docs/02:262` 只有一句话，给了 4 个条件（承诺到期、目标冲突、资源跨阈值、外部高显著事件），且限定在「离线追赶」语境下，不是通用唤醒规范。`scheduler.ts` 只实现了时段转换一种。

**并入要求**：升为通用唤醒条件清单，写入 `docs/02 §3.5`。每个条件必须能指出它读哪个状态、由哪张表触发；无法指出的条件不得写入（防止变成一句好听的原则）。

#### §4.3 离线追赶模拟七步 —— **需并入**

v1 判「直接采纳→M2」但未落任何规范。七步中第 5、6、7 步尤其重要，且项目现役文档没有等价表述：

- 限制级联深度与每个追赶窗口的高显著事件数量（防止离线一个月生成一整季剧情）；
- 不允许无充分因果前置的随机极端、永久性事件，仅因用户离线而发生；
- 生成新快照的同时保留原始事件以便回放和审计。

并入去向：`docs/02 §3.5`。

#### §4.4 事件来源五类 —— **需并入（部分）**

补充分类：系统事件 / 角色计划 / NPC 行动 / 用户通信 / LLM 开放提议。
项目 `origin` 四类：`user` / `scheduled` / `impulse` / `system`。

对照结果：

- 「角色计划」可归入 `scheduled`，但项目目前的 `scheduled` 只有时段转换，没有日程来源。**需并入**：日程作为 scheduled 事件源。
- 「NPC 行动」**项目无对应**，且这是 S7 的直接前置。它依赖 entities 表存在。**需并入**，随 §4.1。
- 「LLM 开放提议」项目已覆盖且更严（模型只提议，`origin` 不因模型输出而改变）。

#### §4.5 真相 / 信念 / 表达三分 —— **需并入（合并为四分）**

项目 `docs/02 §2.5` 是「事实 / 信念 / 承诺」三分；补充是「世界真相 / 主体信念 / 主体表达」三分。两者正交，合并后应为**四分**：事实、信念、承诺、表达。

项目其实已有表达层（`speech` 表 + M4 communication plan），但没有与前三者并列声明，导致「她此刻选择告诉博士什么」在规范上不是一个独立对象。**需并入** `docs/02 §2.5`：补第四类，并明确「她可以暂时不说一件真事」是合法状态，不是遗漏。

#### §4.6 事件账本示例 —— **需并入（`witnesses` 一项）**

项目 `world-event.schema.json` 整体比补充示例严格。但补充示例含 `witnesses`（目击者），项目**没有**这个字段。

`witnesses` 是 §10.3 社会信息传播的前置：没有目击者记录，就无法判断某个 NPC 是否应当知道某件事，「有限认知」只能靠模型自觉。**需并入**，M2，随 entities。

#### §4.7 无脚本剧情的涌现条件六条 —— **需并入**

`docs/05 A10` 已覆盖其中四条。缺两条，且都重要：

- **信息传播依赖目击者和通信，不自动全知**（对应 §4.6 `witnesses`）；
- **同一事件对不同角色具有不同 appraisal**（对应 §6.3）。

并入去向：`docs/05 A10`。

### 3.4 §6 动机、评价、情绪与决策

这一节是本次重裁与 v1 分歧最大的地方。v1 用一行「修订后采纳，拒绝全局 Utility 总分」处理了整章；实际上章内不同小节的性质完全不同，必须分开裁。

#### §6.2 七维 drive 表 —— **拒绝作为常驻刻度**

补充提出 Stability / Safety / Affiliation / Intimacy / Competence / Autonomy / Curiosity 七个 drive，各取 `[0,1]` 连续值，带角色特有目标区间和变化速率。

按判据 1：归属、亲密、自主、好奇是**主观涌现现象**，不是客观事实。按判据 2：一组带目标区间的缺口值会直接进入决策，是在替她做决定。

**这是 v1 留下的口子。** v1 拒绝了九维关系向量（§7.1）和十二项 Utility 求和（§6.5），却没有裁这张表——因为它藏在一个被判「修订后采纳」的条目里。三者是同一种形态，应同样处理。

**改写后形态**：内生动机不另立维度表，从已有对象派生——未决线索（`threads.open` + 停滞时长）、未完成承诺（commitments）、长期关切（`persona` 陈述句）。这些都是**有来源、可指认、可被事件改变**的具体对象，符合 `docs/02 §3` 第 3 步「这些是证据对象，不是刻度」。

需要保留的是 drive 的**思想**而非形态：她有不依赖用户指令的内生目标。这一点项目已由 threads + persona 承载。

#### §6.3 八维 appraisal —— **修订后采纳**

`goal_relevance / desirability / expectedness / agency / controllability / certainty / norm_compatibility / relationship_implication`。

**与 §6.2 的关键区别**：drive 是常驻刻度（每时每刻都有值），appraisal 是**事件级一次性解释**（对某一具体事件的评估，带 source refs，不持久化为角色属性）。它描述的是「这件事对她意味着什么」，不是「她是什么样的人」。判据 1 与判据 2 均不触发。

项目现状：`docs/02 §3` 第 4 步只说「appraisal 更新连续情绪」，没有给结构。`tick-proposal.schema.json` 有 `valence` 与 `intensity`，但没有产生它们的理由结构。

**并入形态**：作为 tick 输出的**可选**结构，每维带 source refs；不得持久化为角色的常驻属性；不得由 appraisal 直接推导动作（判据 3）。

#### §6.4 情绪动力学 —— **部分采纳**

- 四维 `valence/arousal/dominance/approach_avoidance`：**拒绝**。项目已定 `valence + intensity`（`docs/08 §1.6`），二维足够且已进 Schema，四维是无验证依据的扩张。
- 「具名情绪实例记录对象、强度、来源事件和未解决程度」：**需并入**。这让「她还在为某件事别扭」成为可指认对象，而不是一个总的心情值。
- 「未解决事件残余会延长、叠加或转化情绪」：**需并入** `docs/08 §1.6`。
- 禁止单跳映射（一句夸奖直接满好感）：已覆盖。

#### §6.5 十二项 U(a) 求和 —— **拒绝**（维持 v1）

`docs/08 §1.9` 已经要求保存决策日志并列了内容，但没有结构，也没有 Schema。补充的 DecisionTrace 定义（触发事件、候选动作、归一化特征、各项分量、过滤原因、最终动作、世界结果）可直接使用，**但须去掉「各项 Utility 分量」**——项目不产生这个数字。替换为：参与仲裁的承诺/关切来源、被牺牲的选项、显式机会成本。

```sql
    label TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('open','paused','resolved','retired')),
    summary TEXT NOT NULL,
    ...
);
```

并且 `src/gf/state/reducers.ts` 把 `status` 当作主字段、`open` 当作派生值：

```ts
thread.status = value;
thread.open = value !== "resolved" && value !== "retired";
```

**被废除的四值枚举原样回到了已冻结的 DDL，方向还反了**（规范里 `open` 是唯一状态，实现里 `status` 是主、`open` 是派生）。同时缺失 `hook`、`stakes`、`current_state`、`needs_user`、`last_touched_event` 五个字段——其中 `last_touched_event` 是联想采样「未决度权重」的唯一来源，缺了它 `docs/08 §1.4` 的打分函数无法实现。

`docs/08 §5` 的原话预言了这件事：「若它在实现中新增了任何『类别表』『档位』『每日上限』，都要回来确认——那大概率是同一个病的第五次发作。」

**处理**：`migrations/002` 重建 `relationship_threads`，去 `status` 枚举，补五个字段；`reducers.ts` 改为 `open` 为主。这必须在 M1.5 之前完成，否则种子的 5 条线索装不进去。
